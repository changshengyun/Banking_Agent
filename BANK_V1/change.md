# HIRD 手机银行风控系统架构设计与 MVP 原稿整理

## 1. 项目愿景

本项目的目标是构建一个基于 HIRD（Hierarchical Intent-Native Risk Defense）架构的手机银行风控系统。核心方向不是单纯依赖规则拦截，而是通过多智能体与多模态行为感知，逐步识别用户背后的真实意图，实现从“规则判断”到“意图识别”的升级。

## 2. 总体架构

项目最初设想为四层结构：

### 2.1 感知集成层
负责接入端侧与 MCP 汇聚的数据，包括：

- 用户所在城市
- 设备状态
- 账户画像
- 输入停顿与时长
- App 切换与粘贴等行为特征

该层的目标是把原始数据压缩成适合上层决策使用的 `ClientContext`。

### 2.2 认知决策层
负责对交易意图和回复内容做识别与判断。原始设计中包含多个 Agent：

- **领域初步分类 Agent**：先对交易风险场景进行打标，并生成初轮追问。
- **领域场景 Agent**：对接诈骗知识图谱，判断用户回复与既有话术剧本的匹配度。
- **语义分析 Agent**：分析微观行为与文本之间是否存在“知行割裂”。

### 2.3 治理控制层
治理层负责执行确定性规则，避免大模型直接下裁决。其职责包括：

- 风险分数的最终融合
- 状态机路由
- 质询轮数控制
- 安全兜底与人工转接

### 2.4 业务执行层
负责最终动作与结果展示，例如：

- 放行
- 质询
- 拦截
- 生成风险报告

## 3. MVP 设计原稿中的核心逻辑

原始文档将系统设计为一个状态机驱动的风控流程，核心逻辑如下：

1. 接收 `ClientContext` 与用户文本。
2. 并行执行领域场景判断与语义分析。
3. 通过治理层公式计算最终风险分。
4. 按阈值路由到放行、拦截、追问或人工报告节点。

其核心思想是：

- 认知层负责“判断与分析”
- 治理层负责“裁决与执行”
- 所有决策必须可追溯、可审计

## 4. MVP 文档中的技术选型原意

原始设计中提到：

- 使用 LangGraph 作为状态机编排框架
- 使用大模型进行认知层推理
- 使用 MCP 接入上下文与外部情报
- 使用向量数据库承载诈骗知识图谱
- 使用 LLM-as-Judge 方式做测试与验收

这些想法体现出的方向是：

- 以工作流状态机统一风控过程
- 以 Agent 分工替代单体 Prompt
- 以结构化 JSON 输出降低不可控性

## 5. 原始版本中的关键优点

1. **理念完整**：从感知到执行的链路很清晰。
2. **状态机意识强**：能够把风控过程拆成可控节点。
3. **强调确定性治理**：不会把最终裁决完全交给大模型。
4. **有测试意识**：很早就定义了模拟攻击与验收指标。

## 6. 原始版本的主要问题

1. **架构理想化偏重**
   - LangGraph、MCP、向量库、LLM、状态机同时上，落地复杂度很高。

2. **Agent 职责仍有交叉**
   - 领域初分、场景识别、语义分析在早期文档中边界不够干净。

3. **实现与文档不完全一致**
   - 有些能力写在原稿里，但当前实现并未完全达到。

4. **MVP 与长期愿景混写**
   - 原文中既有短期可做内容，也有明显的中长期理想目标。

## 7. 与当前版本的关系

当前项目已经从这个原始原稿演进为更务实的版本：

- 先保留手写 Agent 调度
- 先验证决策质量
- 先把领域初分 / 领域细分 / 语义分析拆开
- Trace 暂时作为审计数据，而不是独立 Agent
- 再考虑后续框架化重构

## 8. 归档结论

这份文档应该被视为项目的**原始蓝图**，不是当前实现说明。它保留的是项目最初的 design intent，适合作为版本对照和架构回溯使用。
